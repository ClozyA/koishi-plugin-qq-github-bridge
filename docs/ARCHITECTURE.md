# 架构与可靠性

## 消息路径

```text
Koishi 前置中间件
  → onebot 平台 / 群聊 / 原始 OneBot 字段交叉核验
  → 中央群绑定解析
  → 管理员、状态、确认、评论的优先级匹配
  → 有界串行队列
  → 持久化事件认领、冷却
  → 审计 pending、权限检查、必要时请求确认
  → GitHub 只读预检 → 一次写入
  → 更新审计 → QQ 纯文本结果
```

普通聊天和不支持的来源交给下游中间件。已识别命令与重复事件被消费。回复用 `h.text()`，不会把 URL、错误或数据库内容解释成 QQ 消息元素。

OneBot 传输端是身份信任边界。交叉核验原始 `user_id`、`sender.user_id`、Session 用户 ID、群号和机器人 ID；用户正文不能参与权限判断。OneBot 服务本身应由部署者正确保护，插件无法防御已被控制的适配器。

## 模块

| 模块 | 职责 |
| --- | --- |
| `config.ts` | 中文 Schema、跨字段校验、敏感输入 |
| `handlers/message.ts` | OneBot 来源、身份、事件时间、文本提取 |
| `utils/parser.ts` | RE2 全文匹配、指令优先级、编号 / 正文校验 |
| `services/repository.ts` | 唯一群号→仓库入口 |
| `services/permission.ts` | 配置超级管理员与数据库普通管理员 |
| `services/storage.ts` | 事件认领、冷却、审计、保留期 |
| `services/github.ts` | Koishi HTTP、端点选择、错误映射、重试、Token 验证 |
| `handlers/commands.ts` | 队列、确认、操作与审计协调 |
| `console.ts` / `rpc.ts` / `client/` | 官方控制台 RPC、鉴权与 Vue 页面 |

## 数据模型 v1

所有表由 `ctx.model.extend()` 注册，使用 Koishi 数据库 API，不直接执行 SQL。

| 表 | 主键 | 数据 |
| --- | --- | --- |
| `qgh_admin` | QQ 字符串 | 添加者、添加时间 |
| `qgh_event` | SHA-256(platform + 群号 + 消息 ID) | 过期时间 |
| `qgh_cooldown` | QQ 字符串 | 下次允许操作时间 |
| `qgh_audit` | UUID | 来源、操作者账号与 QQ、群、仓库、动作、目标、时间、结果、内部原因码 |

群绑定、超级管理员、Token 在 Koishi 插件配置中；普通管理员只有数据库一份真源。`addedBy` 使用真实 QQ 或 `console:ID`，不使用昵称。修改配置触发重新加载，数据库行不清空。

未来增加字段应使用默认值；重命名使用 Minato 的 `legacy` 迁移机制。不可直接改表名造成已有管理员丢失。停用与卸载不删除权限数据；迁移前备份 Koishi 配置和数据库。

## 并发与去重

单实例最多容纳 64 个正在执行 / 等待的命令，串行协调授权变更、权限检查和状态读写。相同仓库由不同群触发也不会在本实例内同时更新。管理员数据主键阻止重复授权。GitHub 写入之间至少间隔 1 秒。

事件执行前先持久化主键认领；重复投递和热重载使用同一条记录。数据库认领失败时不调用 GitHub。发生超时、服务器错误或进程中断后，事件不自动重试。去重默认 24 小时，记录在窗口之外额外保留 60 秒；过旧事件与超过允许时钟偏差的未来事件会被忽略。缺少消息 ID 或时间戳时也不执行。

这是“同一事件至多尝试一次”的策略，**不是跨 GitHub 和数据库的分布式 exactly-once 事务**。认领后进程崩溃可能导致未发布；已提交但响应丢失可能导致结果未知。再次发送一个新 QQ 消息有新的事件 ID，可能产生新评论，因此看到不确定提示时先查 GitHub。评论末尾的内部标记可辅助核对。

不支持多个活跃 Koishi 进程共享本插件数据并同时处理相同群。数据库唯一键能挡住相同事件，但不同事件的权限 / 状态队列不跨进程。人工或其他 GitHub 工具也可能在预检后改状态；最终以 API 的响应为准。

## GitHub 错误与凭据

- 401、403、404、410、422、429、5xx 使用固定中文原因，不返回未经筛选的 API 错误对象、响应体或请求头。
- 网络错误 / 5xx 仅 GET 有限指数退避。403/429 限流根据 `Retry-After` / `X-RateLimit-Reset` 暂停本实例请求，至少暂停一分钟。
- POST/PATCH 不自动重试。写入超时、连接中断、5xx 或响应数据无法证明成功时显示“结果不确定”。
- 评论先 GET 确认目标存在，再 POST `issues/{number}/comments`。PR 普通评论不使用 Review API。
- PR 状态额外读取 `pulls/{number}` 检查 `merged`，再 PATCH 对应端点。接口没有 merge 方法。
- 所有 URL 路径由绑定 Owner / Repo 与数字编号生成。不会跟随重定向去更名或转移后的仓库，部署者需显式更新绑定。
- API 地址只允许 HTTPS，localhost / 127.0.0.1 / ::1 允许 HTTP 测试；拒绝 URL 中的用户名、密码、查询参数和片段。
- 自定义 API 根地址属于部署者的凭据接收方，必须是可信 GitHub Enterprise 或可信代理。对不可信代理的正确性与保密性无法由插件保证。
- 固定身份头与正文分开，昵称转义；正文包含当前部署 Token 时拒绝发布。不会为了脱敏而无声改写正文。

## 审计一致性

重要操作先写 `pending`，成功后写 `success`，无变更为 `noop`，失败为 `failed`，GitHub 结果未知为 `unknown`。确认请求本身是一条无副作用的 `noop`，执行确认后另有实际操作行。

审计起始写入失败会阻止操作。若 GitHub / 权限数据已经变更，而审计结果更新失败，返回“操作已完成，但审计结果更新失败”，保留 pending 供核查，不虚报整个操作失败。突然退出也可能留下 pending。开启审计时应定期查看 pending/unknown；本插件不自动补写 GitHub 操作。

审计不保存评论正文或昵称。每小时按保留天数删除旧审计，同时清理过期去重与冷却记录；启动时也清理。关闭审计不会关闭去重或权限持久化。

## 生命周期和后台安全

插件必需依赖 `database` 和 `http`。停用时移除中间件、取消定时器、关闭队列、丢弃待处理任务、清空确认并中止 HTTP。写入中止仍可能已被 GitHub 接收，因此保留事件认领与不确定结果。

后台通过 `ctx.inject(['console', 'auth'])` 绑定依赖；没有 auth 时不注册页面或管理 RPC。每个 RPC 有官方 authority=5 门槛，并额外读取当前用户和登录会话，防止旧 socket 的缓存权限在账户降权 / 撤销后继续生效。

console 5.30.11 的 `addListener()` 不自动登记清理副作用，本插件在依赖失效或卸载时显式删除本次注册的处理器，且检查处理器身份以免删掉新实例。前后端的权限检查是互补的，隐藏页面不是安全边界。

## 运维排错

| 现象 | 检查 |
| --- | --- |
| 插件等待依赖 | `http` 和数据库是否启用；数据库路径是否可写 |
| QQ 完全无响应 | OneBot 平台名、群绑定启用状态、纯文本、原始数字 QQ / 群号 / message_id / time；不要用控制台 sandbox 代替 OneBot |
| 后台入口不出现 | console 和 auth 是否同时启用，部署管理员是否已登录 |
| 控制台资源 403 | 安装 `.tgz` 到应用 node_modules；源码目录开发使用官方 devMode，不要从任意磁盘路径直接作为生产资源加载 |
| Token 检查可读但写入 403 | 检查两个仓库写权限、Token 所属账号权限、组织审批与 classic PAT 策略 |
| PR 422 | 查看 GitHub 当前状态、是否已合并、源分支是否仍存在；插件不会伪装成功 |
| pending / unknown | 先核对 GitHub 评论 / 状态，再决定是否发一条新的 QQ 指令 |

数据库驱动自身和其他 Koishi 插件可能有独立日志策略；本插件不会把 GitHub 请求对象交给日志。建议以官方 console 的登录、部署网络边界和受控配置备份共同保护统一 Token。
